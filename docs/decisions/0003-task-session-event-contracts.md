# ADR-0003: Task, Session and Event contracts and ACP capability boundaries

Date: 2026-11-17
Status: Proposed (issue #3). Becomes Accepted when the owner approves the PR; implementation details remain provisional until issue #4 builds the first types.

## Context

AgentDock will orchestrate external ACP agents (Claude Code, Codex, Octomind) on a user's repositories. Before writing UI or backend code we need one canonical model of what a task is, what a session is, what is recorded, and what may be claimed after a disconnect or crash. Specifically:

- A Task can involve several Sessions (implementation, review, repair, exploration), and agent context is **not** automatically recoverable.
- External agents own their prompt loop, context and authentication. AgentDock can only rely on what ACP lets them advertise.
- Side effects such as `git push`, PR creation, merges and destructive commands must never happen twice because of a crash or a retry.
- Usage and quota: providers rarely expose subscription allowances. The PRD forbids pretending otherwise.
- The owner's recurring harness needs: resume a quota-stopped session when the quota resets; leave a summary on interruption; a main session with child sessions that are archived only after the user has seen their results (the main session never auto-archives); and three to-do lists — needs reply, needs review, running in background — derived from events.

`docs/architecture.md` sketched entities and a state machine; this ADR makes them precise and machine-checkable.

## Decision

### 1. Contracts live in `docs/contracts/` as JSON Schema plus a transition table

- [`schema/agentdock.schema.json`](../contracts/schema/agentdock.schema.json) defines `Project`, `Task`, `Session`, `Approval`, `Operation`, `Check`, `Usage`, `CapabilitySnapshot`, `EventEnvelope` with one payload per event type, `StreamMessage`, and `AttentionItem`.
- [`transitions.json`](../contracts/transitions.json) lists every legal task and session transition with allowed actors, triggers, durability and conditions.
- Mock fixtures under [`fixtures/`](../contracts/fixtures/) cover all 47 task and 25 session transitions, including disconnect, cancellation, denied approval, quota interruption and host crash. [`validate_fixtures.py`](../contracts/validate_fixtures.py) checks them with the Python standard library only and runs 103 negative mutations (deliberately broken copies of a fixture, each rejected with its expected message). It is a regression check over these fixtures, not the enforcement, and a passing run does not show that an invariant holds; see [Enforcement boundary](#9-enforcement-boundary).
- Naming: `snake_case` keys and enum values everywhere (Rust, SQLite, IPC, TypeScript); event types `<entity>.<past_tense_verb>`; prefixed ULID IDs; RFC 3339 UTC millisecond timestamps; omit absent fields, no `null`. Rust/TypeScript mapping rules: [contracts README](../contracts/README.md#rust-mapping-for-issue-4).

### 2. Task state graph

States: `queued`, `preparing`, `running`, `awaiting_approval`, `verifying`, `review`, `pr`, `ci`, `completed`, `interrupted`, `failed`, `cancelled`. Full graph and conditions: [state-machines.md](../contracts/state-machines.md).

- Terminal (state machine sense: no way out): `completed`, `cancelled`. The UX spec uses "terminal" for the four states whose result the user can view (`completed`, `failed`, `interrupted`, `cancelled`); the archive and attention rules use that UX sense and say so. `failed` is resumable only by an explicit user retry (`T47`). **A retry always restarts from `running`**: `failed → queued` carries no `resume_phase`, so the task goes `queued → preparing → running` and passes verification, review and PR creation again.
- `awaiting_approval` is entered from `running`, `pr` or `ci` and returns to exactly the state it came from (`return_state`). Approvals raised in `verifying`/`review` (review child sessions) and cleanup approvals after the task ended are non-blocking: no `return_state`, no task transition.
- `interrupted` is the single "stopped but resumable" state and always carries an `Interruption` (reason, `phase`, optional retry hint, auto-resume flag, summary, open operations). "Paused" is `interrupted{reason: user_paused}`.
- Resume always goes `interrupted → queued → preparing →` the recorded `resume_phase` (`running`, `verifying`, `review`, `pr`, `ci`), which must be at or before `Interruption.phase` so a resume never skips verification, review or PR creation (`resume_phase` exists only on the resume path; a retry has none). Re-entering `pr`/`ci`, `review → pr`, `pr → ci`, completion and retry all require that no operation of the task is `recorded`, `started` or `outcome_unknown` (reconcile first); entering `ci` additionally requires a push in the current PR round (which starts at `review → pr`) plus a PR.
- Leaving a phase for `interrupted`, `cancelled` or `failed` first closes its operations: recorded ones are abandoned, unused grants invalidated, started ones killed and recorded as `outcome_unknown{cause: killed}`. Exception: a started `pr_merge` is never killed (ADR-0002 PRL-5); Pause/Cancel wait for its result.
- The agent never changes task state. Actor `adapter` is **AgentDock's own adapter component** (the Rust code that speaks ACP to one agent process), never the agent: it records what it observed on the wire. It writes five task transitions itself — `T12` (the agent sent `session/request_permission`) and `T09`/`T14`/`T20`/`T30` (the agent process reported a quota limit, a rate limit or an authentication requirement, exited, or refused a reattach) — because each is the mechanical consequence of a protocol fact that has to be committed in the same transaction as the session event it belongs to. None of them is a workflow decision and none moves a task forward; every other transition belongs to the orchestrator, the user, policy or an integration. Agent text ("approved", "done") is never such a fact.
- Every transition is persisted before it is reported (`persist_then_report`). Transitions that authorize a side effect are persisted before the effect (`persist_then_act`): scheduling, cancellation of a task that has something to stop (cancelling a `queued` or `interrupted` task stops nothing and is `persist_then_report`), approval resolution, entering `awaiting_approval`, resume and retry. This is about AgentDock's own event log; ADR-0002 PRL-5 (the merge report is delivered even if the PR loop's state write fails) concerns the loop's report to the user after a merge that already happened, and is implemented by recording `operation.started` before the merge and reconciling afterwards, never by reporting a task state that was not persisted.

Sessions have their own small graph (including protocol errors while idle, asking for permission or suspended, and closing a session that is still starting; a session that enters `failed` carries outcome `failed` or `cancelled`) — `starting`, `idle`, `active`, `awaiting_permission`, `suspended`, `disconnected`, `closed`, `failed` — with `parent_session_id`, `role`, `outcome`, `supersedes_session_id` and `handoff_summary_id`.

### 3. Three separate notions of "resume"

| | History restoration | External session reattach | Task-level restart |
| --- | --- | --- | --- |
| What | Rebuild the timeline from AgentDock's event log | New process + ACP `session/load` (replays) or `session/resume` (no replay) | Re-enter the workflow with a **new** session seeded by a summary |
| Requires | nothing | the current process advertises `loadSession` / `sessionCapabilities.resume` and an external session id is stored | nothing |
| Session id | n/a | same AgentDock `session_id` | new `session_id`, `supersedes_session_id` |

The UI may only claim an agent session is reconnectable when the capability is advertised by the current process; a failed reattach is recorded as `attach_rejected` and falls back to restart. History re-sent during `session/load` (`provenance: acp_replay`) is accepted only as `session.message_delta`, `session.tool_call` or `session.plan_updated`, and only after a capability snapshot of the process started for this load advertises `loadSession`. "Event replay" (re-projecting events) is always safe; "operation replay" is forbidden. Details: [checkpoint-and-replay.md](../contracts/checkpoint-and-replay.md).

### 4. Event envelope, cursor, backpressure, retention

- Envelope: `id`, `authority_id`, `seq`, `occurred_at`, `recorded_at`, `project_id`/`task_id` (absent only for `system.*`, which carry none of the routing ids), `session_id?`, `type`, `actor`, `provenance` (`live`, `acp_replay`, `recovery`), `causation_id?`, `correlation_id?`, `redaction`, `payload` (already redacted).
- Cursor: `seq` is assigned in the append transaction, strictly increasing and **gap-free per authority**, capped at 2^53 − 1. Readers use `(authority_id, seq)`; a remote worker is its own authority.
- Backpressure: streaming chunks are coalesced; state-changing events are never coalesced or dropped; per-turn output caps produce `session.output_limited`; a slow subscriber gets `lagged` and re-reads from the store; as a last resort AgentDock stops reading the agent's stdout. Nothing is auto-answered under pressure.
- Retention: durable events stay for the task's lifetime; transcript payloads may be compacted into content-addressed artifacts without removing rows (the cursor stays gap-free); `retention_gap` tells a client what is archived. Deleting a task appends `task.deleted` and rewrites the task's earlier events into tombstones (empty payload, same `seq`), so deletion removes content but never creates a gap.
- Redaction before persistence: environment values, MCP `env`/`headers`, auth headers, secret patterns and ACP `_meta` never reach the store; `rawInput`/`rawOutput` only as redacted artifacts.

Details: [events.md](../contracts/events.md).

### 5. Adapter capability detection: ACP v1 stable first

- After every `initialize`, record a `CapabilitySnapshot`: negotiated `protocol_version`, the raw `agentCapabilities` minus `_meta`, and closed boolean `features` derived only from advertised fields (absent = false). Field names were verified against the official ACP schema and Rust schema crate (commits in [acp-capabilities.md](../contracts/acp-capabilities.md#verified-sources)).
- All optional ACP calls (`session/load`, `session/resume`, `session/close`, `additionalDirectories`, `systemPrompt`, prompt media) are gated on the snapshot of the current process.
- ACP v2 (draft) is opt-in per adapter behind a flag and version negotiation; v1 stays the default and is kept side by side. This PR checks v1 only: the validator rejects a `track: v2_draft` snapshot, and the v2 mapping in acp-capabilities.md is a plan. The AgentDock contract is protocol-neutral so v2 maps into the same events; one known gap (v2's optional `stopReason`) is listed below.

### 6. Approvals and non-repeatable operations

- Approvals come from ACP `session/request_permission` (`acp_permission`) or from host policy (`host_policy` for push, PR, merge, destructive commands). An approval is persisted as `pending` before the user sees it and its resolution is persisted before the agent is answered or the operation runs. Only `user` or `policy` actors can approve or deny; agent text never can. Approvals for `pr_merge`, `branch_delete`, `worktree_remove` and `destructive_command` can be granted **only by the user**; policy may deny them or let them expire, and every policy decision names its rule. ACP requests carry `operation_kind: tool_call` and a backend-computed `classified_kind`; classes `pr_merge`, `force_push`, `branch_delete`, `worktree_remove`, `destructive_command` and `unclassified` are user-only. A task has at most one blocking approval. This covers what reaches AgentDock: an agent in its own bypass/full-access mode is not intercepted (ADR-0002 APR-11, issue #26), and client-method execution as Operations is issue #8.
- Every side effect AgentDock controls is an `Operation` with `repeatability` (bound to its kind by the schema: git/PR/merge/branch/worktree/destructive kinds are always `non_repeatable`; repeatable work is a `Check`), an `idempotency_key` = sha256 of canonical `{kind, identity}` (identity = the `target` without its human-readable `description`, i.e. the kind's identity fields including optional ones such as `branch_delete.remote`) that equals the approval's `operation_fingerprint`, and a read-only `reconcile_strategy`. Each kind may only be recorded and started in specific task states (push/PR in `pr`, merge in `ci`, destructive commands in `running`, cleanup after the task ended). An operation id executes at most once (`recorded → started → …`, or `recorded → abandoned` when it never starts); an approval with scope `once` is consumed by one execution, only for an operation of its own task and before its `expires_at`; `git_push` starts only from a clean checkpoint at `expected_sha`, and `pr_merge` only at the SHA AgentDock pushed; a duplicate key is allowed only as an explicit `supersedes_operation_id` of an abandoned, failed-without-effect or reconciled-not-applied/undeterminable operation, with a new approval (one exception, rule 5 of [checkpoint-and-replay.md](../contracts/checkpoint-and-replay.md#rules): an `outcome_unknown` operation whose repeatability is `idempotent_with_key` may be superseded without reconciliation, because the target deduplicates by the key). `operation.succeeded`/`operation.failed` and check results are written only by the orchestrator or the integration that ran the work; whether a reported `failed{effect: none}` is true cannot be seen in the log and is the backend's responsibility (issues #7/#10).
- **After a crash nothing is replayed automatically**: pending approvals and approved-but-unused grants become `invalidated`, recorded operations become `abandoned`, started operations become `outcome_unknown`, running checks become `outcome_unknown`, live sessions become `disconnected`, in-flight tasks become `interrupted{host_crashed}` with auto-resume disabled. These are the only events the recovery actor may write; it never reports a result (`operation.succeeded`/`failed`, a passed or failed check), and `system.recovery_completed` is written by the recovery actor itself. Reconciliation happens later, live and read-only, and resuming into `pr`/`ci` waits for it.

### 7. Usage and quota

- `Usage.source` is exactly one of `provider_reported`, `locally_estimated` (requires an `estimator`), or `unknown` (no numbers allowed). ACP v1 `usage_update` maps to `context_window {used, size}` and `cost {amount, unit}`; credits are never converted to money.
- The UX spec (`docs/ux/states-and-indicators.md` section 8) shows five source tags; the contract has three `Usage.source` values. **Provider-reported**, **Estimated locally** and **Unknown** are `provider_reported`, `locally_estimated` and `unknown`. **Not applicable** (the mock adapter) is not a usage value: an adapter whose registration says it has no usage concept emits no `usage.reported`, and the UI derives the tag from the adapter id. **Sign-in needed** is not a usage value either: the UI derives it from the account's latest task or session state (`interrupted{reason: auth_required}`), and no `usage.reported` is written for it. Neither derivation is checked by the validator.
- There is **no field for remaining subscription quota** anywhere in the contract; the validator rejects keys that match a deny-list of names (`FORBIDDEN_NAME`), which is a name check, not a proof. The UI shows subscription quota as unknown.
- Limits appear only as interruptions: `quota_exhausted` / `rate_limited` with a `retry_hint` whose `source` is `provider_reported`, `user_configured` or `unknown` (unknown carries no time).

### 8. Harness scenarios

- **Resume at quota reset**: `auto_resume_armed` only for quota/rate limits, only with the task's opt-in and a provider-reported or user-configured `not_before`; the orchestrator resumes with `scheduled_resume` no earlier than that time. `task.policy_updated` lets the user turn this off later, which disarms a waiting task.
- **Summary on interruption**: `session.summary_recorded{purpose: interruption}`; host-generated by default because a quota-stopped agent cannot write one; used as the handoff for a restarted session.
- **Main and child sessions**: `parent_session_id`; archiving follows the UX spec (`docs/ux/states-and-indicators.md` section 5): a child is auto-archived only when it is `closed` with outcome `succeeded`/`cancelled`, the user opened its result and never restored it; parent-less sessions, sessions in state `failed` and interrupted ones are never auto-archived; a child can be archived by hand when it is finished (`closed`/`failed`) or interrupted (`suspended`/`disconnected`); a main session can be archived by hand only when its task is `completed`, `cancelled`, `failed` or `interrupted` for a reason other than `user_paused` (a running, queued, paused or awaiting session must be stopped first); a waiting session is unarchived by the system in the same transaction.
- **Three to-do lists**: `AttentionItem` (`needs_reply`, `needs_review`, `background`) is derived purely from events by the rules in [attention.md](../contracts/attention.md); every fixture asserts its expected items. A phase that is not progressing (`phase_decision_pending`), a running task without a live agent (`session_unavailable`), output-limit cancellations (`output_limited`) refusals of any session role and operations with unknown outcome (`reconcile_needed`) are surfaced as needs-reply items, not hidden as background work. The three kinds map to the UX inbox sections; deliberate differences are listed in attention.md and below.

### 9. Enforcement boundary

`validate_fixtures.py` is a **regression check over the committed fixtures, nothing more**. **A passing run does not show that an invariant holds.** It shows two things only: the 13 committed fixtures obey the rules the script implements, and each mutation named below (a deliberately broken copy of one fixture) is rejected with its expected message. A stream the validator accepts is not thereby safe, and a rule is claimed here only as far as a named mutation exercises it.

The full guarantees — in particular crash recovery, retry, reattach, non-repeatable operations and user-only approvals — are owned by the Rust backend: the core store checks invariants when an event is written (issue #7), the approval policy classifies and decides requests (issue #8), and the PR loop (issue #10) owns the probes and the review/merge checks. The right-hand column lists the tests those issues must add; property-based or state-machine tests are asked for where examples cannot cover the input space.

## Alternatives considered

1. **Prose-only contracts in `architecture.md`.** Fast, but drift is guaranteed and nothing checks the fixtures. Rejected.
2. **Rust types as the only source now.** Issue #4 owns the Rust workspace; creating crates here would pre-empt it. The schema is the interim source; #4 decides Rust-first or schema-first generation (README).
3. **A separate `paused` state.** Two resumable states with nearly identical rules; folded into `interrupted{user_paused}`.
4. **Allow `failed` to be terminal.** Users regularly retry after fixing an environment problem; making retry an explicit, recorded user transition keeps history intact.
5. **Optimistic UI for state changes.** Simpler perceived latency, but it breaks "denied action does not execute after reload" and crash recovery. Only streaming text may appear before commit.
6. **Per-session cursors.** Easier sharding, but cross-entity ordering (approval vs. operation vs. state change) matters more. One cursor per authority.
7. **Auto-retry non-repeatable operations with provider idempotency.** Not available for `git push`/merge/destructive commands; reconciliation + human decision is the only safe general rule.
8. **Model quota as "remaining %" with a disclaimer.** Contradicts PRD and AGENTS.md; rejected.

## Consequences

- Implementation (#4, M2) gets a precise target and a ready conformance suite (fixtures + expectations).
- Every optional agent feature must go through capability snapshots; adapters cannot "just know" an agent supports resume.
- More events and more explicit user decisions after failures (reconcile, resume, retry). This is intentional friction.
- The JSON Schema subset validator is not a full JSON Schema implementation; CI in #4 should add a full validator.
- Proposed numbers (buffer sizes, retention, caps) are placeholders to be measured, not commitments.

## Open questions (owner decision needed)

1. Is folding "Paused" into `interrupted{user_paused}` acceptable, or should `paused` be a first-class state?
2. Should `failed → queued` (retry) stay, or should a retry create a new task linked to the failed one?
3. Default `auto_resume_policy`: both off (current proposal) or `on_quota_reset` on by default?
4. Rust-first (`schemars` + `ts-rs`) vs schema-first (`typify` + `json-schema-to-typescript`) generation for #4.
5. When v2 support starts: allow `turn_ended` without `stop_reason` (v2 makes it optional), or add an explicit `unreported` value?
6. Retention defaults (64 MiB transcript per task, 30 days after terminal) and output caps (8 MiB / 20,000 events per turn) — acceptable starting points?
7. Which host-policy approvals may a policy rule grant without a human? Current proposal: `pr_create`, `pr_update`, `pr_comment`, `external_write` may be policy-approved; `git_push` (never force) only through a rule the user created, because ADR-0002 APR-10 puts push in the default ask set; `pr_merge`, `branch_delete`, `worktree_remove`, `destructive_command` are user-only. Making `git_push` user-only as well is a one-line change in the validator and the classification table. The same question applies to ACP permission requests: classes `git_push` and `config_write` are in ADR-0002 APR-10's default ask set but are not user-only classes here, so a policy rule can approve them.
8. A task has at most one blocking approval at a time (`awaiting_approval` holds one `approval_id`; the validator rejects a second one). If two sessions of a running task ask for permission at once, the second request is held by the adapter until the first is resolved. Acceptable, or should `awaiting_approval` track a set?
9. Attention items that differ from the UX spec ([attention.md](../contracts/attention.md#divergences-from-the-ux-spec-owner-decision)): an armed auto-resume is shown as background, not as a result to review; `phase_decision_pending`, `session_unavailable` and `reconcile_needed` are treated as awaiting-input (the UX state table maps Review/CI to running); an interrupted (`suspended`/`disconnected`) child session has no review item of its own, the task-level item covers it; quota, rate-limit and sign-in stops are `interrupted`, not `failed`; `preparing` is listed as a workflow step, not as queued; a finished agent turn and an output-limit stop count as awaiting-input. Keep, or follow the UX spec?
10. Undo of the bulk "Mark completed as reviewed" (UX section 4) has no event yet. Issue #7 needs one (for example an acknowledgement-revoked event) before the bulk action ships.
11. An archived session that goes back to work without waiting is not unarchived: an archived main session whose task is `interrupted` with an armed auto-resume returns to `running` at the reset time, and an archived suspended sub-task can be continued; in both cases the session stays archived and its background items stay hidden (only waiting unarchives, UX-47). Options: forbid archiving while auto-resume is armed, or have the system unarchive on `T44`/`S17`. Not decided here.
12. A task that was already `interrupted` with an armed auto-resume (`quota_exhausted` / `rate_limited`) before a host crash is left alone by recovery and may still be resumed with `scheduled_resume` once due, although a recovery-written interruption is never auto-resumable. Keep (the user opted in and the interruption is not a crash), or have recovery disarm it (a recovery write that would have to be added to the whitelist)? The wording of checkpoint-and-replay.md and the schema now says exactly this; the semantics are unchanged.
13. An `idempotent_with_key` operation that is `outcome_unknown` may be superseded (checkpoint-and-replay.md rule 5), but the superseded operation stays `outcome_unknown` and keeps blocking `no_unreconciled_operations` until it is reconciled. Should a superseded operation count as reconciled, or is the second attempt only a way to learn the outcome, with reconcile still required? No fixture exercises the exception.
14. `S10` requires the approval to belong to the session, and `S09`/`S14` require that the session has no other pending approval, so an adapter forwards one `session/request_permission` of a session at a time (see also question 8 for tasks). Acceptable for ACP agents that send parallel permission requests?
