Claude Code 與 OpenAI Codex 跑的是同一種 agent loop（模型提出 tool call、harness 執行、結果附加回 prompt，直到模型給出最終回覆），真正的差異落在四個地方：編輯工具格式與自家模型的耦合（Claude 用唯一匹配的字串替換，Codex 用模型「extensively trained」的 `apply_patch`）、對 prompt cache 的工程紀律、安全預設（Claude 以 classifier 審查的 auto mode 為預設，shell 沙箱需手動開且原生 Windows 不支援；Codex 預設 workspace-write 加無網路沙箱，且有原生 Windows 沙箱），以及對外整合協定（Claude 靠 Agent SDK 與第三方 ACP adapter，Codex 自建 App Server JSON-RPC 協定、ACP 同樣由 Zed 的 adapter 提供）。「Claude Code Desktop 比較好用」的說法幾乎全部來自社群軼事與功能清點，指向意圖理解、可回溯的 checkpoint、hooks 廣度、diff 逐行評論與計畫可見性；受控研究則顯示同一模型換 harness，解題率平均只差 2 到 5 個百分點、與重跑一次的雜訊相當，穩定可見的差距在 token、時間與成本。「Codex 比較好用」的證據集中在價格、限額、精簡輸出與 Windows 原生沙箱。其他十幾個 harness 各自貢獻一兩個可移植的機制，例如 Orca 的狀態證據時鐘、Grok Build 的 dashboard 就地回答權限、Muse 的 per-turn checkpoint、OpenMausBot 的跨引擎權限等級映射與委派契約。對 AgentDock 而言，值得做的是工作台層與流程層（狀態、決策收件匣、worktree 生命週期、diff 回饋、獨立 review、委派與用量呈現），不是重做 loop、編輯格式或程式碼索引；模型選擇建議採「四個能力等級＋跟隨 agent 預設」，再把「平行編排」與「權限等級」做成獨立的兩個軸，具體模型對應一律在執行期由 agent 回報的能力決定。

## 迴圈幾乎相同，分歧在編輯格式、快取紀律與對外協定

兩家都公開把「harness」定義為模型外面那一層。Anthropic 把 Claude Code 定義為包在模型外、負責提供工具與管理模型所見 context 的那一層，並說明 terminal、Desktop、IDE、雲端與 Remote Control 底下跑的是同一個 agentic loop（[How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)）【官方文件】。OpenAI 的 Michael Bolin 把 Codex 描述成標準迴圈：模型要嘛產生最終訊息、要嘛請求 tool call，結果附加回 prompt 後再查詢，每個新 turn 都送出完整歷史（[Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)）【工程部落格】。所以「誰的 loop 比較聰明」不是有意義的比較軸，差異在 loop 周圍的設計選擇。

**快取是兩家共同的第一原則，但落實方式不同。** Anthropic 自述整個 Claude Code harness 圍繞 prompt caching 建構，把 plan mode 做成 `EnterPlanMode`／`ExitPlanMode` 兩個工具而不是切換唯讀工具集，因為換工具集會讓快取失效；變動資訊以 `<system-reminder>` 附在訊息尾、MCP 工具只送名稱 stub、壓縮時沿用父對話完全相同的前綴，並對 cache 命中率設警報、過低就宣告 SEV（[Prompt caching is everything](https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/)）【工程部落格】。Codex 的做法是每次請求完全 stateless、不用 `previous_response_id`，理由是支援 Zero Data Retention；reasoning 以 `encrypted_content` 帶回，prompt 只 append 不改前綴，中途改工具、換模型、改 sandbox／approval mode 或 cwd 都會破壞快取（[Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)）【工程部落格】。Claude Code 官方另列出會讓快取失效的操作：切換模型、在多數模型上切換 effort（Fable 5.1+、Opus 5.5、Sonnet 5.5、Haiku 5.5 在 API key 或訂閱下例外）、壓縮與升級版本；切換 permission mode、呼叫 skill、`/rewind`、spawn subagent 則保留快取（[Prompt caching](https://code.claude.com/docs/en/prompt-caching)）【官方文件】。推論：任何會在 session 中途改變外部 agent 工具清單、模型或 system prompt 的工作台動作都是成本事件，AgentDock 的 UI 應該把「換模型」「換 effort」標示成會重建快取的操作，而不是無成本的下拉選單。

**編輯工具是最明確的「工具與模型綁定」證據。** Claude Code 的 Edit 是精確字串替換，不用 regex 或模糊比對，要求 read-before-edit 與唯一匹配（[Tools reference](https://code.claude.com/docs/en/tools-reference)），語意與 API 端的 Anthropic-schema 工具 `str_replace_based_edit_tool` 一致（[Text editor tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/text-editor-tool)）【官方文件】。Codex 的 `apply_patch` 不用行號、以前後三行 context 與 `@@` 定位，OpenAI 明說這是推薦格式，而且模型已針對它大量訓練（[GPT-4.1 Prompting Guide](https://developers.openai.com/cookbook/examples/gpt4-1_prompting_guide)）【官方文件】。Cursor 的工程文章提供了旁證：它在模型切換時會換用該模型專屬的 tool 格式，OpenAI 模型用 patch、Anthropic 模型用 string replacement（[Cursor: Continually improving our agent harness](https://cursor.com/blog/continually-improving-agent-harness)）【工程部落格】。其他工具設計也看得出哲學差異：Claude Code 在 macOS／Linux 把 Glob 與 Grep 收回 Bash（內嵌 bfs 與 ugrep），只在 Windows 保留專用工具；Bash 輸出超過約 30,000 字元就存檔並只給預覽；WebFetch 由另一個模型讀頁面再回答問題（[Tools reference](https://code.claude.com/docs/en/tools-reference)）。Codex 的 web search 預設走 OpenAI 維護的 cached index，理由是降低來自即時內容的 prompt injection，而且 Codex 明說不 sandbox MCP tools（[Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)；[Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/)）【官方文件】【工程部落格】。

**模型與 harness 的共同調校，兩家公開的程度不同。** Anthropic 的 postmortem 證實它在每個模型發布前都會針對該模型調整 harness 與產品，也證實 harness 層的三個小改動（預設 effort 由 high 降到 medium、每輪清掉舊 thinking 的快取 bug、一條降低冗長度的 system prompt 指令）就造成可感知的品質下滑，事後承認降 effort 是錯誤的取捨並回滾（[April 23 postmortem](https://www.anthropic.com/engineering/april-23-postmortem)）【工程部落格】。工具可用性也按模型分流：Task 工具只在 Opus 4.7、Sonnet 4.6、Haiku 4.5 以前預設開啟，理由是新模型不需要書面清單也能追蹤多步驟工作，而工具定義會佔 context（[Tools reference](https://code.claude.com/docs/en/tools-reference)）【官方文件】。但「Claude 模型在 Claude Code 確切工具集上做 post-training」**找不到 Anthropic 一手證據**；官方只說 Claude Code 建立在 bash 與 text editor 這兩個 Claude 已擅長的工具上（[Harnessing Claude's intelligence](https://claude.com/resources/articles/harnessing-claudes-intelligence)），agentwiki 關於 ForgeCode 的說法無法核實。前次研究中，Armin Ronacher 回報 pi 的巢狀 `edits[]` 工具讓 Opus 4.8 約 20% 呼叫失敗、開 strict tool invocation 後消失，並推測新模型後訓練包含 Claude Code（[Ronacher](https://lucumr.pocoo.org/2026/7/4/better-models-worse-tools/)，前次研究 2026-11-16 讀取）【社群】，這是推測不是證據。OpenAI 方面，GPT-5-Codex 公告明說它特別針對 code review 訓練，並建議只在 Codex 或類似環境做 agentic coding（[Introducing upgrades to Codex](https://openai.com/index/introducing-upgrades-to-codex/)）【工程部落格】，但 2026-11 的推薦模型已換成 `gpt-6.2-sol`、`gpt-6.2-astra` 等，模型頁沒有再宣稱與 harness 共同訓練（[Models](https://learn.chatgpt.com/docs/models)）【官方文件】。推論：可以確定的是「harness 隨模型調整」，而且這些 per-model 調整是封閉的；AgentDock 透過 ACP 驅動未修改的官方 CLI，正好把這層調校原封不動保留下來，前提是不在外面疊加隱藏 prompt 或暗中改 effort。

**對外協定是 AgentDock 最直接受影響的差異。** OpenAI 先試過把 Codex 包成 MCP server 給 VS Code，發現很難讓 MCP 語意符合 VS Code 的需求，才自建 App Server：雙向 JSON-RPC 2.0、以 Thread／Turn／Item 為原語、含 `turn/steer`、`turn/interrupt`、`review/start`、`thread/fork`、`thread/compact/start` 與反向 approval 請求，桌面 app、VS Code、Web worker 都是它的 client；`codex mcp-server` 已移除（[Unlocking the Codex harness](https://openai.com/index/unlocking-the-codex-harness/)；[App Server](https://learn.chatgpt.com/docs/app-server)；[Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)）【工程部落格】【官方文件】。同一篇文章評價跨供應商的 agent harness 協定可攜但傾向只支援共同能力；OpenAI 官方文件沒有提 ACP，ACP 支援來自 Zed 維護的 `codex-acp`（[Zed blog](https://zed.dev/blog/codex-is-live-in-zed)）【社群】。Claude Code 在 ACP 官方 agents 清單上同樣是經 adapter 列出（[ACP Agents](https://agentclientprotocol.com/get-started/agents)），前次研究記錄社群要求原生 ACP 的 issue 被以「not planned」關閉（[claude-code #6686](https://github.com/anthropics/claude-code/issues/6686)，前次研究 2026-11-16 讀取）。推論：AgentDock 的兩個主要 runtime 都是「官方 CLI＋第三方 adapter」，adapter 的能力子集與版本追趕是常態風險，App Server 直連能拿到 review、fork、compaction 事件等更完整的能力，但要評估 known-clients 名單要求與版本釘選（[App Server](https://learn.chatgpt.com/docs/app-server)）。

## 安全與工作台：Claude 靠 classifier，Codex 靠預設沙箱

下表把使用者指定的十一個面向並排。除特別標示外，Claude 欄來自 code.claude.com 官方文件與 Anthropic 部落格，Codex 欄來自 learn.chatgpt.com 官方文件與 OpenAI 部落格。

| 面向 | Claude Code（CLI／Desktop Code 分頁） | OpenAI Codex（App／CLI／IDE／App Server） |
|---|---|---|
| Agent loop 與中斷 | 單一 loop；`Esc` 取消執行中工具，或直接輸入修正、同一 turn 內讀到（queued）；每次編輯前檔案快照，`Esc` 兩次回溯（[How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)） | stateless 請求＋加密 reasoning；`turn/steer` 追加輸入、`turn/interrupt` 結束 turn；中斷父 turn 保留子 agent 已排隊回覆（[App Server](https://learn.chatgpt.com/docs/app-server)；[Changelog](https://learn.chatgpt.com/docs/changelog)） |
| 計畫與 effort | Plan mode 是工具＋system message；effort `low`～`max`，5.5 世代預設 `medium`、thinking 無法關閉，`ultrathink` 只提升當回合（[Model configuration](https://code.claude.com/docs/en/model-config)） | `update_plan` 工具與 plan item 串流；effort Light、Medium、High、Extra High、Max、Ultra，**Ultra 會用 subagents 拆成平行工作**（[Models](https://learn.chatgpt.com/docs/models)） |
| 工具設計 | 字串替換 Edit、PowerShell 工具、LSP plugin、Monitor、WebFetch 由次級模型摘要；工具回應預設上限 25,000 tokens（[Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)） | `apply_patch`、sandboxed shell、unified exec（長生命週期 session，工具名只見第三方來源）、cached web search；MCP 不受沙箱約束 |
| Context 與 compaction | CLAUDE.md 疊加不覆寫、`@import` 最多四層、建議每檔少於 200 行；只有 AGENTS.md 沒有 CLAUDE.md 時才讀 AGENTS.md；多數模型原生 1M；壓縮以相同前綴 fork（[Memory](https://code.claude.com/docs/en/memory)） | AGENTS.md 由 project root 到 cwd 每層至多一份、近者在後，總量上限 32 KiB；server 端 `/responses/compact` 回傳加密 compaction item；預設 context 272,000（Astra）或 500,000（Sol）（[AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)；[Models](https://learn.chatgpt.com/docs/models)） |
| Subagents | 預設背景執行、最多三層巢狀、可 `isolation: worktree`；agent teams 實驗性；dynamic workflows 由 Claude 寫 JavaScript 編排，預設 16 並行、禁用 `Date.now()`／`Math.random()` 以便重放（[Subagents](https://code.claude.com/docs/en/sub-agents)；[Workflows](https://code.claude.com/docs/en/workflows)） | TOML 自訂 agent；**繼承父 turn 的 sandbox 與 approval，agent 檔不能覆寫**；等所有結果到齊再彙整（[Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)） |
| Skills／hooks／plugins／MCP | hooks 事件多（OpenChamber 清點 33 種），handler 可為 command、http、mcp_tool、prompt、agent；逾時預設 fail-open；官方明言護欄要放在 hooks，CLAUDE.md 裡的指示只是請求（[Hooks](https://code.claude.com/docs/en/hooks)；[Extend Claude Code](https://code.claude.com/docs/en/features-overview)） | 14 種 hook 事件，只執行 command 與 mcp_tool；非 managed hooks 信任綁 hash；`PreToolUse` 可改寫輸入但不支援 `ask`；官方稱 tool hooks 是有用的護欄、但不是完整的強制邊界；plugin 目錄與 ChatGPT 共用（[Hooks](https://learn.chatgpt.com/docs/hooks)；[Skills & Plugins](https://learn.chatgpt.com/docs/skills-and-plugins)） |
| 權限與沙箱 | 六種模式，v2.1.283 起 auto mode 為 terminal 與 VS Code 預設起點，classifier 看不到 tool results；deny 在 bypass 下也生效；shell 沙箱預設關、**原生 Windows 不支援**；Anthropic 自稱內部減少 84% 提示（[Permission modes](https://code.claude.com/docs/en/permission-modes)；[Sandboxing](https://code.claude.com/docs/en/sandboxing)；[Beyond permission prompts](https://www.anthropic.com/engineering/claude-code-sandboxing)） | 預設 workspace-write、網路關閉、`.git`／`.agents`／`.codex`／`.aws` 唯讀；`untrusted` 已退役；Windows 優先 MXC（需 Win11 24H2/25H2 特定 build）；可設 `auto_review` reviewer agent，錯誤時 fail closed（[Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)；[Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)） |

這張表最值得 AgentDock 注意的是兩條安全哲學的分歧。Claude Code 的縱深防禦是「確定性規則→機率性 classifier→只涵蓋 shell 的 OS 沙箱→critical path 硬規則」，classifier 刻意剝除 tool results，讓檔案或網頁裡的惡意內容無法直接操縱它；官方同時警告 auto mode 只減少權限提示、不保證安全（[Permission modes](https://code.claude.com/docs/en/permission-modes)）。Codex 則把「技術上能做什麼」（sandbox）與「何時問人」（approval policy）拆開，approval 從枚舉演進成 `on-request` 加上依類別（sandbox、rules、MCP、skill）細分的 granular 表（[Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)）。在 Windows 上，這個差異會變成實質差距：Claude Code 原生 Windows 執行指令時沒有沙箱、官方建議改用 WSL 2（[Setup](https://code.claude.com/docs/en/setup)），Codex 有原生 MXC，但 MXC 會在前景指令結束時終止子程序，detached dev server 可能失敗（[Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)）。Claude Code 在 Windows 上還有一個跨工具耦合陷阱：在有 Git Bash 的 Windows 上，任何 Bash deny 規則都會讓 PowerShell 工具在沒有警告的情況下整個關閉（[Tools reference](https://code.claude.com/docs/en/tools-reference)）。推論：AgentDock 以 Windows 為優先，不能假設 ACP agent 自帶 shell 沙箱；權限 UI 應明確顯示每個 agent 目前的原生模式、沙箱實作與「哪些工具因哪條規則被移除」，Rust 後端只對工作台自己控制的動作（worktree、git、PR、檔案寫出、permission 回覆）強制政策。

工作台層兩家已經高度重疊：平行 session、worktree 隔離、diff 行內評論、背景任務檢視、排程收件匣都是標配。推論：差異化不在「有沒有 worktree」，而在 worktree 的生命週期規則（Codex 的 detached HEAD、延後建分支、先 snapshot 再刪、pinned 不刪，比 Claude Desktop 的 30 天延遲清理更保守），以及 review 迴圈是否能串到 PR 與 CI。值得一提的反面教材是 Claude Code CHANGELOG 中多起 worktree 誤刪檔的修正，包括 `ExitWorktree` 曾刪除其他 session 正在使用的 worktree、Remote Control 在 worktree 模式停止時會刪除 git-ignored 的 `.env`（[CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)），這說明 worktree 清理是高風險區域。另一個會在 2026 年底困擾比較的事實是 Codex 的產品邊界正在移動：官方文件已改稱「ChatGPT desktop app／ChatGPT Work」，但 changelog 仍以「Codex app 26.1120」與「Codex CLI 0.172.0」發版，兩者是否正式合併，官方頁面沒有明說（[App](https://learn.chatgpt.com/docs/app)；[Changelog](https://learn.chatgpt.com/docs/changelog)）。

把這些產品放在一起看，有三個趨勢。第一，「一個 harness、多個表面」已是主流：Copilot 把所有表面收斂到同一個 runtime，Codex 把所有 client 收斂到 App Server，Claude Code 則宣稱所有介面的 loop 相同。第二，跨廠商工作台（Orca、OpenMausBot、Goose 的 ACP provider）都遇到同一組問題：權限模式要逐引擎映射、能力子集要探索、session ID 要對映、vendor 擴充要降級。第三，最好的設計都把「人類回饋」聚合成一次 turn：Orca 的批次 diff 評論、Grok Build 的 approve w/ comments、Claude Desktop 的 `Ctrl+Enter` 一次送出、Grok Bot 把對外副作用變成可批次處理的卡片。推論：AgentDock 自身的差異化空間在「Windows-first＋Rust 後端強制政策＋以 ACP 同時驅動 Claude Code 與 Codex」，上述跨廠商工作台都是 Electron，Grok Build 是單一廠商 TUI，Grok Bot 是雲端閉源。

## 模型選擇的等級區分：一套定義同時服務導航與任務包

### 各家都收斂到三到五個 effort 等級，外加一個「自動」

證據顯示，「等級」在各家產品裡至少有三種不同的意思，混在一起會造成誤解。第一種是**推理強度（effort）**：Claude Code 對 Fable、Opus 5.5、Sonnet 5.5、Haiku 5.5 等支援 `low/medium/high/xhigh/max`，5.5 世代預設 `medium`，Opus 4.7 預設 `xhigh`（[Model configuration](https://code.claude.com/docs/en/model-config)）；Codex 是 Light、Medium、High、Extra High、Max、Ultra，Luna 支援 Max 不支援 Ultra（[Models](https://learn.chatgpt.com/docs/models)）；Grok Build 以 ACP 標準 `configOptions` 暴露 `reasoning_effort`（`minimal`～`xhigh`）（[agent mode](https://github.com/xai-org/grok-build/blob/2bdd1d6a6369de0e8c68132ea4539e9abd9e14a8/crates/codegen/xai-grok-pager/docs/user-guide/15-agent-mode.md)）；Copilot Fusion 是 Standard、High、Max，另有不能手動選的 Fast，High 與 Max 需 Pro+ 以上（[Copilot Fusion](https://docs.github.com/en/copilot/concepts/models/copilot-fusion)）；Cursor Bugbot 是 Low、Default、High、Smart（[Bugbot](https://cursor.com/docs/bugbot)）。第二種是**編排強度**：Codex 的 Ultra「會用 subagents 把任務拆成平行工作」，Claude Code 的 `ultracode` 觸發 dynamic workflow（[Workflows](https://code.claude.com/docs/en/workflows)），Fusion 的 Cascade 與 Critique 是多模型編排；這些會倍增成本，本質上不是「更努力想」而是「開更多 agent」。第三種是**權限等級**：OpenMausBot 的 Ask for approval、Auto-accept edits、Approve for me、Full access、Custom（[approval levels](https://github.com/milind-soni/OpenMausBot/blob/54ab8e3afafe4460a9c6d5241e498d849de3d318/docs/approval-levels.md)），它決定 agent 能做什麼，和模型強弱無關。

角色分工的證據則指向「便宜模型做探索、強模型做判斷」。Muse 的 lead／sidekick 自稱一個 session 中以 Opus `agent` subagent 花約 $44、等價 sidekick 約 $0.30，並據此在 Lead 模式封鎖 `agent` 工具（[lead-sidekick plan](https://github.com/honvl/muse-code-gui/blob/7e267605ab9b156e65d73c762cecd7a5419a9b01/docs/lead-sidekick-optimization-plan.md)），但 64% 的整體節省只來自 3 個 thread 且以假設換算。Copilot 的遷移數據顯示約 61% 的 tool call 來自 subagent、探索與修改約 10:1（[Rust migration](https://github.blog/ai-and-ml/migrating-the-github-copilot-runtime-to-rust-using-copilot/)）。Cursor 量到用更貴的模型做 context 摘要，品質差異可以忽略，所以沒採用（[Cursor harness](https://cursor.com/blog/continually-improving-agent-harness)）。LangChain 的「reasoning sandwich」是規劃與驗證用高 reasoning、執行用中等 reasoning（[LangChain](https://blog.langchain.com/improving-deep-agents-with-harness-engineering)）。Aider 的 architect／editor 組合在多數配對上優於單模型（[architect](https://aider.chat/2024/09/26/architect.html)）。Claude Code 自己的內建 subagent 也分級：claude-code-guide 與 web-fetch 用 Haiku，auto mode classifier 預設 Claude Sonnet 5（[Subagents](https://code.claude.com/docs/en/sub-agents)；[Permission modes](https://code.claude.com/docs/en/permission-modes)）。反方向的警訊同樣明確：Anthropic 把預設 effort 由 high 降到 medium 稱為錯誤的取捨並回滾（[April 23 postmortem](https://www.anthropic.com/engineering/april-23-postmortem)），表示「預設用最便宜的」對實作任務不安全。

切換時機的證據一致指向「在邊界換、不要在中途換」。Fusion 只在 cache 邊界或對話複雜度大幅變化時才換模型（[Copilot Fusion](https://docs.github.com/en/copilot/concepts/models/copilot-fusion)）；Cursor 建議同一對話盡量用同一個模型，需要換時開新 context 的 subagent（[Cursor harness](https://cursor.com/blog/continually-improving-agent-harness)）；Claude Code 與 Codex 都把換模型列為破壞快取的操作。最後，Grok Bot 是另一個極端：它自行為每個任務選模型，使用者不能選，團隊 allowlist 也不適用（[FAQ](https://docs.x.ai/grok-bot/faq)）。推論：這種完全隱藏的路由與 AgentDock「no hidden model interception」的原則衝突，AgentDock 即使做自動路由，也必須把選中的等級與具體模型寫進 timeline。

### 等級定義與導航規則：改由 ADR-0005 定義

草案（`T-default` 加 `T1`～`T4`、與「編排軸」「權限軸」分開、執行期依 agent 回報的能力表對應具體模型、換不到就降級並寫事件、不自動升級、訂閱額度顯示「未知」、中途換等級會重建快取）已整理成 [ADR-0005](../decisions/0005-model-tiers.md)（Status: Proposed）。**等級的唯一定義在 ADR-0005**，本文件不再重複，避免兩處漂移。產品導航與 `docs/tasks/` 任務包的模型建議共用這一套等級，ADR-0005 也說明 PR #68 的 `S`／`S/R`／`St` 如何對應。

與本研究直接相關的結論：

- 證據支持把「模型能力」「編排」「權限」拆成三個獨立的軸（Codex Ultra 與 Claude Code `ultracode` 屬編排，不是更強的模型）。
- 預設應是「跟隨 agent 預設」，因為 effort 預設值會隨模型世代改變，且 Anthropic 自己的 postmortem 顯示 harness 層的小改動就會造成可感知的品質變化。推論：AgentDock 暗中改 effort 是反模式；使用者明確選擇的等級是例外，且要記錄。
- **`claude-agent-acp` 與 `codex-acp` 是否暴露 model／effort config options 尚未查證**（筆記只證實 Grok Build 會）。查證方法與阻擋關係寫在 ADR-0005 的 open question 1，建議以新 issue NI-H1 追蹤。
- 具體模型名稱（例如 Fable、Opus 5.5、Sol、Astra）在筆記中沒有可靠的相對能力與價格證據，只能當 2026-11-27 的範例，不得寫死。


## Conclusion

這輪研究改變了一個常見的直覺：「Claude Code 比較好用」不等於「Claude Code 的 harness 讓模型更會解題」。受控研究把 harness 的平均解題效果壓到重跑雜訊的範圍內，留下來穩定可見的是成本、時間與互動體驗；而互動體驗正好是 AgentDock 這種外層工作台能夠擁有、又不必攔截外部 runtime 的部分。換句話說，AgentDock 透過 ACP 驅動未修改的官方 CLI，等於把兩家封閉且隨模型調整的 loop、工具格式與 prompt 調校原樣保留，再把差異化集中在官方 app 各自只能做到自家 agent 的地方：跨廠商一致的狀態、權限等級、決策收件匣、worktree 與 checkpoint 的保守生命週期，以及從計畫、實作、獨立 review 到 CI 的完整迴圈。代價是永遠落後於 adapter 的能力子集，所以「能力探索與誠實降級」不是附加功能，而是整個產品可信度的地基。

第二個值得帶走的判斷是 Windows。Claude Code 在原生 Windows 沒有 shell 沙箱，Codex 有但 MXC 會殺掉背景子程序，OpenCode 仍建議 WSL；Windows-first 的工作台在這裡沒有現成答案可抄，能做的是如實顯示每個 agent 的真實安全邊界、用 Job Object 這類機制管好程序生命週期，並把 privileged 動作留在 Rust 後端。模型等級的設計也遵循同一個邏輯：把能力、編排、權限拆成三個看得見的軸，讓使用者與實作 agent 共用同一套語彙，而不是把路由藏起來替使用者決定。
